# 편성 · 대본 · shots.json

Stage 2(편성)와 Stage 3(대본)의 규칙. 이 스킬의 산출물이 "영상 코드"가 아니라 "대본과 영상이 같은 길이인 한 벌"이 되게 하는 부분이다.

---

## 1. 편성 (Stage 2)

### 입력 조합별 기본 편성

| 입력 | 편성 |
|---|---|
| **논문만** | ① 문제제기 ② 핵심 아이디어 ③ 방법(수식) ④ 결과·한계 — 3~4편 |
| **코드만** | ① 실행 흐름 따라가기 ② 핵심 함수 해부 ③ 텐서 shape 변화 — 2~4편 |
| **둘 다** | 논문 편성 + 마지막에 "논문의 수식이 코드 어디에 있는가" 대조 편 1개 |

### 규칙

- **한 편 = 한 아이디어.** 편 제목을 한 문장으로 못 쓰면 쪼갠다.
- 한 편 5~8분. `sum(run_time + wait)` 기준 300~480초.
- 편당 구간(Scene 클래스) 4~7개. 구간 하나가 90초를 넘으면 나눈다.
- 1편은 반드시 **문제부터** 연다. 방법론으로 시작하지 않는다.
- 편 사이에 의존이 생기면 앞 편을 20초 안에 요약하는 구간을 넣는다. "지난 편에서…"로 넘기지 않는다 — 시청자는 한 편만 볼 수 있다.

### CP1 승인 양식

편성안을 이 형태로 제시하고 사용자 승인을 받는다.

```
[1편] 이 논문이 풀려는 문제                     약 6분  (구간 5개)
      선형 판별의 한계 → 왜 비선형이 필요한가
      쓸 자료: 논문 §1, Fig.1(p9 크롭)
[2편] ...
```

## 2. 대본 톤 (Stage 3)

- 구어체 존댓말. "~합니다", "~죠", "~볼까요".
- **질문으로 열고 화면으로 답한다.** "왜 이게 문제일까요?"
- 한 문장 = 한 화면 변화. 두 가지가 동시에 바뀌면 문장을 쪼갠다.
- 수식은 **읽지 말고 의미를 말한다.** "분자는 클래스 간 분산입니다" ○ / "W 트랜스포즈 S b W" ✕
- 전문용어는 첫 등장 1회만 병기: "국소 이웃(local neighborhood)".
- 논문에 없는 주장을 하지 않는다. 비유는 비유라고 말한다.
- 숫자·성능은 논문에 적힌 값만. 반올림하더라도 원값을 함께 둔다.

### 금지

- "매우 뛰어난 성능", "혁신적인" 같은 자기 홍보 형용사. 수치와 비교 대상으로 말한다.
- 다른 연구를 깎아내리는 표현.
- 확인되지 않은 인과 주장 ("~때문에 성능이 올랐습니다" → 논문이 ablation으로 보인 것만).

## 3. shots.json 스키마

에피소드 폴더에 하나. 대본·타이밍·에셋의 단일 출처다.

```json
{
  "video": "ep01_problem",
  "title": "이 논문이 풀려는 문제",
  "scenes": {
    "intro": {
      "shots": [
        {
          "id": "intro_s01",
          "narration": "분류기를 만들 때 가장 먼저 마주치는 문제부터 봅시다.",
          "visual": "제목이 나타난 뒤 위로 올라감",
          "code_hint": "Write(kr(title)) → title.animate.to_edge(UP)",
          "est_sec": 4.2,
          "run_time": 1.5,
          "wait": 2.7,
          "asset": null
        }
      ]
    }
  },
  "total_sec": 312.4
}
```

| 필드 | 의미 |
|---|---|
| `id` | `<scene>_sNN`. 로그·검수에서 컷을 지목하는 키 |
| `narration` | 실제로 읽을 문장. 이게 대본이다 |
| `visual` | 화면에서 일어나는 일을 한국어로 (사람이 읽는 콘티) |
| `code_hint` | 코드 생성기가 참고할 Manim 표현 |
| `est_sec` | `estimate_narration.py`가 채움. 낭독 예상 시간 |
| `run_time` | 애니메이션 길이. **반드시 명시** |
| `wait` | `max(0.2, est_sec - run_time)`. 스크립트가 채움 |
| `asset` | `null` / `{"kind":"pdf_crop", ...}` / `{"kind":"generated","prompt":"..."}` |

### 작업 순서

```bash
# 1) narration만 채운 shots.json을 쓴다
# 2) 타이밍 자동 계산
python scripts/estimate_narration.py --shots shots.json --write
# 3) 경고 확인: run_time >= est_sec 인 컷은 문장을 쪼개거나 run_time을 줄인다
# 4) main.py 생성 → 스모크 렌더
```

`estimate_narration.py`는 한국어 5.5음절/초를 기준으로 하고, 쉼표 0.25초·마침표 0.55초의 쉼을 더한다. 영어 단어는 2.5글자당 1음절, 숫자는 자릿수×1.3으로 센다("2024" → 이천이십사).

낭독 속도를 바꾸려면 `--rate`로 조절한다. 실제 녹음이 일관되게 빠르거나 느리면 한 번 측정해서 값을 고정할 것.

## 4. 길이 검증

렌더 후 `verify_output.py`가 실제 mp4 길이와 `sum(run_time + wait)`를 비교한다. **오차 15% 초과면 REWORK.**

**+4~8%의 체계적 초과는 정상이다.** 씬을 연결하는 전환 컷(화면 정리, 위치 이동 등 나레이션이 없는 `playw(..., wait=0.0)`)은 `shots.json`에 없지만 실제 영상에는 들어간다. 실측 결과 편당 +4~8%가 여기서 나왔다. 즉 15% 허용치의 절반은 이미 전환 컷이 먹고 들어가므로, **나레이션 컷 자체의 오차 예산은 사실상 ±7%**라고 보고 편성해야 한다. 전환 컷이 많은 편이라면 `shots.json`에 `narration: ""`인 컷으로 명시해 예상치에 포함시키는 편이 낫다.

오차가 나는 흔한 원인:
- `run_time`을 명시하지 않아 `Write()`가 텍스트 길이에 비례해 늘어남
- `self.play`를 그냥 써서 `wait`이 안 붙음
- `clear()`가 raenim 버전이라 1초 대기가 추가로 들어감
- 3D 카메라 이동 헬퍼가 내부에서 `wait`을 또 호출함
