# 실패에서 배운 것 — 546차시 / 70GB 를 올리며 실제로 터진 문제들

전부 실측이다. 여기 적힌 걸 안 지키면 같은 자리에서 막힌다.

## 1. Notion API 는 통합앱당 ~3 req/s

병렬로 돌리면 `429 rate_limited` 가 나고, **한 번 걸리면 몇 분간 전체가 막힌다**.
스레드 4개로 페이지를 읽다가 이걸 맞았고, 복구에만 수 분이 걸렸다.

- `vt_common.api()` 가 0.42초 간격 스로틀 + 429 시 `30초 × 시도횟수` 대기를 한다. **직접 urllib 로 호출하지 말 것.**
- 더 중요한 건 **호출 수 자체를 줄이는 것**. 로컬에 있는 정보로 복원 가능하면 API 를 부르지 않는다.

## 2. rclone 업로드가 회선을 독점해 Notion API 를 굶긴다

상한 없이 돌렸더니 **두 번 다 ~185MiB 지점에서 회선이 멎었고**, 동시에 Notion 호출도 응답이 끊겼다.
업로드를 죽이자 즉시 살아났다 — 원인이 이것으로 확정됐다.

- Notion 작업과 병행할 땐 `--bwlimit` 필수(업링크의 60~70%). 업로드만 남으면 `--bw off`.

## 3. rclone 이 구글드라이브 업로드 중 자주 정체된다

수 GB 지점에서 전송량이 수백 B/s 로 떨어지고 `--timeout` 으로도 안 풀린다.
**8시간에 22번** 발생했다. 그냥 두면 하루를 날린다.

- 내장 워치독이 3분간 전송량이 안 늘면 rclone 을 죽이고, 상위 루프가 재개한다. `copy` 는 멱등이라 안전하다.
- **`--stats` 를 5m 로 두면 워치독이 정체를 못 읽는다.** 반드시 `1m`.
- 워치독 임계값은 6분보다 **3분이 총 처리량에 유리했다**(빨리 끊고 재시작하는 게 낫다).

## 4. 그룹별로 순회하면 미완성 그룹을 건너뛴다

주차마다 rclone 을 돌리고 N회 재시도 후 다음으로 넘어가게 짰더니,
0_사전학습(33/69)·1주차(18/47)가 미완성인 채로 넘어가 버렸다. 로그만 보면 정상으로 보인다.

- **전체를 한 번에 copy 하고, 남은 파일이 0 이 될 때까지 라운드를 반복**한다. 실제로 43라운드가 걸렸다.

## 5. 드라이브 공개는 폴더 단위로 한 번

파일별 `rclone link` 는 수백 개면 수십 분이 걸린다.
`rclone link --expire 0 <폴더>` 한 번이면 하위 전체가 공개된다.

## 6. 노션 영상 임베드는 `video` 블록이 아니라 `embed` 블록

`video` 블록은 Google Drive 링크를 거부한다.
`embed` + `https://drive.google.com/file/d/<ID>/preview` 를 쓴다. 재생 확인 완료.

## 7. 블록 append 는 `after` 파라미터를 지원한다

이 덕분에 **페이지를 먼저 만들고 영상·대본을 나중에 끼워 넣는** 설계가 가능하다.
70GB 업로드가 끝날 때까지 페이지 생성을 기다릴 이유가 없다.

```python
{"children": [...], "after": "<앞 블록 id>"}
```

## 8. 노션 블록 한계

- 한 요청 **100블록** — 중첩 children 까지 세어 계산해야 한다(`count_blocks`). 보수적으로 85.
- `rich_text` 는 블록당 **2000자**. 대본은 1800자 단위로 문단을 끊는다.
- `column_list → column → 블록` 이 이미 2단계라, 그 안에 toggle+children 을 넣으면 3단계가 돼 거부된다.
- 깨진 lone surrogate 가 섞이면 `400 no low surrogate`. `desurrogate()` 로 제거한다.

## 9. Windows 환경

- **`.ps1` 을 BOM 없이 저장하면 PowerShell 5.1 이 ANSI 로 읽어 한글 경로가 깨진다.** 장시간 작업 러너는 Python 으로 짤 것.
- `wmic` 는 최신 Windows 에 없을 수 있다. 프로세스 조회는 `psutil` 이나 `tasklist` 를 쓴다.
- 분리 실행은 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` + `stdin/stdout/stderr=DEVNULL`.

## 10. 서브에이전트 완료 메시지는 믿지 말 것

"대기 중입니다", "이제 파일을 작성합니다" 같은 응답을 완료로 보고한다.
**산출 파일의 존재와 내용으로 판정한다.**

## 11. 작업 큐를 쓴다면 stale 반납에 시간 가드를 둘 것

진행 중인 클레임까지 풀면 중복 작업이 난다. "N분 이상 묵은 것만" 반납하게 해야 한다.

## 12. 화질 질문에는 두 원인을 구분해서 답할 것

노션에서 어떤 영상은 720p, 어떤 건 320p 고정으로 보이는 현상은 원인이 두 개다.

| 원인 | 판별법 | 해결 |
|---|---|---|
| **드라이브 변환 대기** | Drive API `videoMediaMetadata` 가 비어 있음 | **기다리면 저절로.** 로컬 작업 불필요 |
| **원본이 저화질** | 로컬 ffprobe 로 높이 < 1000 | 영구적. 업스케일해도 정보는 안 생김 |

`probe_quality.py` 가 둘 다 조사한다. 실측 사례: 546개 중 변환 대기 118개 + 원본 720p 이하 33개.
드라이브는 업로드 후 360p → 480p → 720p → 1080p 순으로 변환하며, 대량 업로드 직후엔 대기열이 밀린다.

## 13. 메타데이터 길이가 0 인 차시가 있다

강의 플랫폼 메타데이터에 `duration: 0` 이 섞여 있었다. `probe_duration` 으로 ffprobe 실측을 켜 두거나,
나중에 `05_fill_missing.py --fix-duration` 으로 고친다.
