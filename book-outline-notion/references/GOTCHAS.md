# 실패에서 배운 것 — 497쪽 보고서를 Notion으로 옮기며 실제로 터진 문제들

전부 실측이다. 여기 적힌 걸 모르면 같은 자리에서 막힌다.

---

## 1. 목차 깊이를 그대로 DB 행으로 옮기면 못 쓴다

7단계 725행을 한 DB에 넣었더니 화면에 **725행이 평평하게 펼쳐져** 목차를 훑을 수가 없었다.
계층을 relation 속성으로만 표현하면 **사람 눈에는 아무 계층도 안 보인다.**

- **DB 행은 3단계까지**(`BOOK_MAX_DB_LEVEL=3`). 그 아래는 페이지 본문의 H2/H3 소제목이 맞다.
- 문서의 논리적 계층 ≠ 사람이 탐색하기 좋은 깊이. 497쪽 보고서 기준 36행이 적당했다.
- 폴더처럼 파고들려면 **부모 행 페이지 안에 인라인 DB를 만들고 자식을 그 안에 둔다.**
  최상위 DB에는 대분류만 남는다.

## 2. Notion '하위 항목(Sub-items)'은 API로 못 켠다

토큰 권한 문제가 아니다. 워크스페이스 소유자 권한으로도 안 된다 — **공개 API에 그 필드가 없다.**
아래 3가지를 모두 시도했고 전부 HTTP 200을 주고 **조용히 무시**한다.

```
PATCH /v1/data_sources/{id}   {"sub_items": {...}}
PATCH /v1/databases/{id}      {"sub_items": {...}}
relation 속성에 is_sub_item_relation: true
```

→ 그래서 이 스킬은 **인라인 DB 중첩**으로 계층을 만든다. UI 토글이 필요 없고 결과도 더 낫다.

## 3. HWP로 만든 PDF는 물리적 한 줄이 각각 하나의 block

블록 경계로는 문단을 못 나눈다. 문단 시작 신호는 불릿 마커(`▣`)뿐이고 나머지는 이어짐이다.

**줄을 이어붙일 때 띄어쓰기는 줄 끝 공백으로 판단한다.** HWP는 단어 경계에서 줄을 바꿀 때
줄 끝에 공백을 남기고, 음절 중간에서 끊을 때는 남기지 않는다.

| 앞 줄 | 뒤 줄 | 결과 |
|---|---|---|
| `'…추론, 판단, 문제 해결 '` (공백 있음) | `'능력을…'` | `문제 해결 능력을` |
| `'…소프트웨어 기술이 아'` (공백 없음) | `'니라…'` | `기술이 아니라` |

한글 여부로 판단하는 휴리스틱은 **틀린다**. `학습 성능`+`향상`은 띄고 `성능 제`+`공`은 붙여야
하는데 둘 다 한글+한글이다. 반드시 원본의 공백 신호를 써야 한다.

**예외 2가지** (497쪽에서 각 1건씩만 발생 — 그래서 규칙으로 넣어도 안전하다):
- 양쪽 정렬로 구두점 뒤 공백이 삼켜짐 → 앞이 `.,!?;:` 로 끝나고 뒤가 글자면 공백을 넣는다
- 좁은 표 셀에서 영문 단어 사이 공백이 사라짐 → 영문+영문이면 공백을 넣는다

## 4. 표 셀의 줄바꿈은 `extract()` 로는 못 고친다

`find_tables().extract()` 는 셀 안의 줄을 `\n` 으로 이어 붙여 준다. 그러면
`'학습 성능\n향상'`(공백 필요)과 `'성능 제\n공'`(공백 불가)을 **구분할 수 없다.**

→ `t.rows[i].cells` 의 bbox 로 `page.get_text("dict", clip=...)` 해서 셀을 **다시 읽어야** 한다.
그래야 위 3번의 공백 신호를 셀 안에서도 쓸 수 있다.

## 5. 표는 쪽 경계에서 두 개로 쪼개진다

`find_tables()` 는 쪽이 넘어가면 별개 표로 잡는다. 뒤쪽 조각에는 캡션이 없고,
`자료:` 출처가 뒤 조각에만 붙어 **출처가 엉뚱한 표에 달린 것처럼 보인다.** (497쪽에서 43건)

→ 캡션 없는 표가 직전 표 바로 뒤(같거나 다음 쪽)에 **같은 열 수**로 나오면 이어 붙인다.
이어지는 쪽에 머리행이 반복되면 제거한다.

## 6. "표"인데 실제로는 이미지인 것이 섞여 있다

`[표Ⅲ-15]` 캡션이 있는데 `find_tables()` 가 0개를 반환하는 경우가 있다(497쪽에서 11건).
캡션 아래가 **이미지로 그려진 표**다.

→ 캡션 아래 여백으로 판별한다. **진짜 표는 캡션 바로 아래(≈10pt)에 셀 텍스트가 오고,
이미지는 200pt 넘게 비어 있다.** 여백이 40pt 이상이면 그림과 똑같이 크롭·OCR 처리한다.

관련: 캡션 바로 밑 `(단위: 억 달러)` 같은 짧은 괄호 주석이 여백 계산을 막는다.
캡션의 일부로 흡수해야 도식을 잘라낼 수 있다.

## 7. 그림은 텍스트 레이어가 비어 있다 → OCR이 실제로 필요하다

크롭 영역 234개에서 추출되는 텍스트가 **0자**였다. 도식 안의 라벨·수치가
검색에도 요약에도 전혀 안 잡힌다는 뜻이다.

→ 크롭 PNG를 비전 모델로 판독해 `🔍 도식 내용` 토글로 넣는다. 그래야 검색된다.
판독 결과는 요약 단계의 입력으로도 넣어 그림 내용을 아는 상태로 요약하게 한다.

## 8. Codex CLI 배치 호출 함정 3가지

1. **프롬프트는 stdin으로 넘긴다.** `-i/--image` 가 가변 인자라 뒤에 붙인 위치 인자(프롬프트)까지
   이미지로 삼켜 `No prompt provided via stdin` 으로 실패한다.
2. **결과는 `-o/--output-last-message <FILE>` 로 받는다.** stdout에는 훅 로그(`hook: SessionStart`)가
   섞여 파싱이 깨진다.
3. **Windows에서는 `shutil.which("codex")` 로 실경로를 해석한다.** npm 배치파일(`codex.CMD`)이라
   subprocess가 이름만으로는 못 찾는다.

`--output-schema <JSON Schema>` 로 응답 구조를 강제하면 파싱 실패가 사라진다.

## 9. 배치 키를 인덱스로 잡으면 재개가 깨진다

`ocr_0000.json` 처럼 **인덱스로 키를 잡으면**, 대상 목록에 항목이 추가돼 순서가 밀렸을 때
기존 산출물이 엉뚱한 배치로 재사용돼 **새 항목이 영원히 처리되지 않는다.**

→ 키는 **내용에서 뽑는다**(예: 배치 첫 항목의 id). 그리고 "이미 처리된 것"을 먼저 모은 뒤
**미처리분만 배치**한다.

## 10. 페이지 이동은 본문과 속성을 보존한다

`POST /v1/pages/{id}/move` 로 페이지를 다른 DB로 옮기면 **블록과 속성값이 그대로 남는다**(실측).
덕분에 본문 재업로드 없이 구조만 재편할 수 있다.

- 단, **대상 DB에 같은 이름·타입의 속성이 있어야** 값이 살아남는다. 스키마를 먼저 복제할 것.
- relation 속성은 DB가 갈리면서 사라진다(중첩 구조에서는 어차피 불필요).

## 11. Notion API 한도

- 평균 **3 req/s**. `notion_api.py` 가 0.34초 간격 스로틀 + 429 백오프를 한다. 직접 호출하지 말 것.
- rich_text 한 조각 **2,000자**, 배열 100개, children 1,000개/요청, 페이로드 **500KB**.
- 중첩 children까지 세어 **85블록**씩 자르는 게 안전하다(`chunked_append`).
- OCR/LLM 산출물에 섞이는 **lone surrogate** 는 `400 no low surrogate` 를 일으킨다 → `desurrogate()` 필수.

## 12. Python 출력이 버퍼링돼 진행률이 안 보인다

백그라운드로 돌리며 로그 파일을 보면 **한참 비어 있다가 한꺼번에 찍힌다.**
`python -u` 를 쓰거나 `print(..., flush=True)` 를 쓸 것. 상태 파일로 진행률을 보는 것이 더 확실하다.

## 13. 목차 첫 항목 하나로 쪽번호 오프셋을 정하면 오판한다

표 목차·그림 목차 페이지에도 `Ⅰ. …` 같은 대분류 제목이 그대로 있다.
첫 항목만 찾으면 거기에 걸려 **본문 시작을 24쪽으로 잡는다**(실제 43쪽).

→ 목차·표목차·그림목차 구간을 **모두 지난 뒤부터** 찾고, 항목 여러 개(40개)의
오프셋 **최빈값**을 쓴다. 일치율이 60% 미만이면 경고를 띄운다.
